# Bigarr

Unified media library manager: one application that replaces, brick by brick, Radarr, then Sonarr, Seerr, Tautulli and Prowlarr.

What Bigarr fixes at the model level: a movie can have **several versions** in the same instance (1080p, 4K, Director's Cut…), each monitored, searched and upgraded on its own. On the way out, Bigarr exposes **Radarr and Sonarr v3 compatible APIs** so Seerr, Bazarr and the rest of the ecosystem plug in without noticing.

- Status: **early, in active development**. Films and series are managed end to end (search, download, import, upgrades), and existing Radarr, Sonarr and Tautulli setups can be imported. The compatible API speaks Radarr's dialect for films and Sonarr's for series.

## Stack

C# / .NET 10, ASP.NET Core minimal APIs, EF Core + SQLite, React + Vite + TanStack (tooled with Bun), multi-arch Docker image. GPL-3.0.

## Development

```bash
# backend — http://localhost:7979
dotnet build
dotnet test
dotnet run --project src/Bigarr.Api

# front — Vite dev server proxying /api to the backend
cd web && bun install && bun run dev

# production build of the front, served by the backend from wwwroot
cd web && bun run build
```

Metadata comes from TMDB. Set `Bigarr__Tmdb__ApiKey` (a v3 API key or a v4 read access token, free at themoviedb.org). Without it Bigarr runs on an embedded fixture catalogue of a dozen films, which is what the tests use.

Series are numbered by TVDB, the numbering releases and files use, with TMDB for images and ids. Set `Bigarr__Tvdb__ApiKey` (a TVDB v4 project API key; no subscriber PIN needed). With the TMDB key alone, episodes follow TMDB's order; with neither key, a small fixture catalogue of shows is used.

Metadata is refreshed by the daily *Refresh metadata* task (`Bigarr__Metadata__RefreshIntervalHours`, 24), which follows Radarr's rule: a film never refreshed (every film a Radarr import brings) or refreshed more than 180 days ago is due, one refreshed less than 12 hours ago is not, and in between only the films whose dates can still move are asked again: announced, in cinemas, or released less than 30 days ago. Never-refreshed films go first, then the oldest; TMDB is asked at most `Bigarr__Metadata__RefreshFilmsPerSecond` (4) times a second and every film is saved as soon as it is refreshed, so the first run after a large import can be stopped and resumes where it was. A film that fails stays due for the next run; `Bigarr__Metadata__RefreshMaxConsecutiveFailures` (10) failures in a row stop the run and raise a health issue until a run goes through. The refresh only rewrites metadata: a new title or year renames no folder, and versions, monitoring and files stay as they are. It does not run on the fixture catalogue, which would flag every film it does not know as deleted.

Releases come from Torznab indexers, normally **pushed by Prowlarr** the way it feeds a Radarr. In Prowlarr, Settings → Apps → + → **Radarr**: *Prowlarr Server* is Prowlarr's URL as Bigarr reaches it (`http://prowlarr:9696` on a shared Docker network), *Radarr Server* is Bigarr's URL as Prowlarr reaches it (`http://bigarr:7979`), *API Key* is a Bigarr key with the `default` view, created in Settings → Connect, *Sync Level* is **Full Sync**, and the default *Sync Categories* (the Movies ones) fit. Prowlarr then adds each of its torrent indexers that can search movies, pointing at its per-indexer Torznab endpoint, rewrites their name, priority, categories, minimum seeders, seed criteria and RSS and search switches when they change on its side, and removes them when they go; Settings → Indexers marks them as managed by Prowlarr, and only their rate limit stays as set in Bigarr. Usenet indexers are refused since there is no usenet client yet: give the Bigarr application and the torrent indexers a common tag in Prowlarr so only those are sent. `Bigarr__Prowlarr__BaseUrl` and `Bigarr__Prowlarr__ApiKey`, with which Bigarr used to read Prowlarr's indexer list itself, are now ignored: the indexers created that way stay, and Prowlarr takes them over on its first sync instead of duplicating them. Indexers can still be added by hand (any Torznab endpoint, such as Jackett's, plus its API key). If an SSO proxy sits in front of Prowlarr, exempt `/<id>/api` and `/<id>/download` from it: Prowlarr's own API key protects those paths. Without a tracker at hand, add an indexer of type **Mock**: it fabricates a realistic list of releases for any film, including a few that must be rejected, so the search screen can be exercised offline.

Quality profiles rank qualities and score **custom formats**. A custom format recognises a trait of a release (group, codec, HDR, language, size…) through conditions built by hand in Settings → Custom formats, where each profile also gets its score. The JSON shape is Radarr's, so Radarr exports and [TRaSH guide](https://trash-guides.info/Radarr/) files import unchanged (Import JSON, or `POST /api/v1/customformats/import`); the guide's suggested score is shown next to each profile and applied only on click. Every search, feed pass and file is judged with the formats from then on. Nothing is stored per release: editing a format or a score changes the next page.

The **RSS loop** is what fills the library day to day: every indexer's feed is polled (every 15 minutes by default, `Bigarr__Rss__IntervalMinutes`, never below 10), every release of the feed is matched to a film of the library, judged for every monitored version (profile, custom format score, size, seeders, constraints, blocklist, current file) and attributed to one version; the best release of the pass for each version is then sent to a download client. Like Radarr, each pass judges the whole feed again, not only what is new: a release turned down because its film was not available yet, its version unmonitored or its file already good enough is taken as soon as that changes, as long as the feed still carries it. Activity → Releases shows every release seen once, with its latest verdict per version and whether it was grabbed. One feed request per indexer per pass, never one per film. A fresh torrent often has no seeders yet: when a version would take a release but for its seeders, the pass plans one quick recheck of that indexer's feed 5 minutes later (`Bigarr__Rss__QuickRecheckMinutes`, 0 turns it off). The recheck never plans another one, and a whole pass that comes first takes its place.

**Searches** cover what the feed missed. A film or version added with *Search on add* is searched right away in the background; the *Search* button on a movie page or in Movies → Wanted queries every indexer with automatic search enabled and grabs the best approved release; and the *Search missing and cutoff unmet* task (hourly, `Bigarr__Search__CutoffUnmetIntervalMinutes`) goes through Movies → Wanted, monitored versions without a file or below their profile's cutoff, with a backoff per version that doubles after each empty search (one hour, two, four… up to a week, `Bigarr__Search__BackoffBaseMinutes` / `BackoffMaxHours`) and at most `Bigarr__Search__CutoffUnmetBatchSize` (20) versions per pass, so a tracker never sees a full sweep of the library. The movie page's **interactive search** is for the film: every indexer is queried once and each release shows how it fits every version, with the reasons. Its grab button names the version the release goes to (the one that accepts it, like the RSS attribution, otherwise the closest), and the arrow next to it sends it to another version or to a new one-shot version. A text typed next to the search button replaces the film's ids and titles, for a film listed under another name or spelling; the releases are still judged against the film's versions, and one whose title does not match is flagged but can be grabbed by hand. Grabbing a release that the version rejects, or that is not the film, asks first and lists the reasons. Columns sort by clicking their header. A series page has the same search for the whole show, a season or one episode (the buttons on the header, on each season and on each episode row): every release shows the episodes it covers, whether it is a season pack, its quality, languages, custom formats and their score, and how each version judges it.

A **failed download** (the client reports an error, or the torrent stays stalled longer than `Bigarr__Downloads__StalledTimeoutMinutes`, off by default) is blocklisted for its version (a one-shot feeds its film's default version), removed from the client with its files (`Bigarr__Downloads__RemoveFailedDownloads`), and replaced by an automatic search (`Bigarr__Downloads__SearchAfterFailure`). The blocklist is per managed version: the 1080p and the 4K of a film keep independent lists. Activity → Blocklist lists the entries and lets them go; a release removed from the queue by hand can be blocklisted the same way.

Downloads go through **qBittorrent** (WebUI API v2, 4.1 or later). Add it in Settings → Download clients with its host, port, credentials and the category Bigarr should own (created if missing); several clients are tried by priority. Grab a release from a film's interactive search: Bigarr fetches the `.torrent` (or passes the magnet), sends it with the category and records the grab, so the download is still followed after a restart. Activity → Queue is a live view of what the clients hold in that category (server-sent events; `Bigarr__Downloads__PollSeconds`, 10 by default): progress, ETA, the client's warnings, and a remove action that can also delete the files and blocklist the release. A torrent deleted by hand in qBittorrent leaves the queue after three polls and the version goes back to missing. Without a qBittorrent at hand, a download client of type **Mock** completes its downloads on its own after a minute and a half and writes a small file for the import to pick up.

A finished download is **imported**: Bigarr finds the video in what the client wrote (samples skipped), checks it is an upgrade over the version's current file, **hardlinks** it into the version's folder so the torrent keeps seeding (copy when the two paths are on different filesystems, or move if you prefer), names it from the template in Settings → Media management (Radarr's token syntax, `{Movie Title} {(Release Year)} {edition-{Edition Tags}} {[Quality Full]}` by default, plus `{Version}`; Radarr's *Replace Illegal Characters* and *Colon Replacement* settings apply to every name, with Sonarr's own copy, custom colon included, for series), probes it with ffprobe when available (codecs, channels, HDR, languages; the Docker image ships it, otherwise install ffmpeg), and moves the replaced file to the **recycle bin** when one is configured. One-shot versions stop monitoring once their file is in. A refused import (lower quality, no video, path not reachable) stays visible in the queue with its reason and is never blocklisted: **Import by hand** shows what Bigarr made of each file, lets you pick the movie, version and quality, and forces it. A completed torrent found in the category without a grab is matched by its title the same way. Files can be renamed later to the current template from the movie page, deleted to the recycle bin, and the history of every version (grabbed, imported, upgraded, renamed, deleted) is under Activity → History and on each movie page.

Every business fact (film added, release grabbed, file imported or upgraded, download or import failed, file deleted or renamed, version settings changed, default version changed, health issue raised or gone) is written to an **outbox** in the same transaction as the change, then delivered to whoever listens: the browser over `GET /api/v1/events` (server-sent events, so pages refresh on their own) and **webhooks**. Settings → Notifications holds the endpoints: a URL, the events it wants (or all of them), and an optional secret; each POST carries `{ eventType, eventId, occurredAt, instance, data }` with the event's snapshot (film, version, release, file…) in `data`, the headers `X-Bigarr-Event` and `X-Bigarr-Delivery`, and `X-Bigarr-Signature: sha256=<hex HMAC-SHA256 of the body>` when a secret is set. A delivery that fails is retried with an escalating delay (1, 5, 15, 60 minutes… `Bigarr__Notifications__RetryDelaysMinutes`, up to `Bigarr__Notifications__MaxAttempts`, 10); the retry state is the row itself, so a delivery pending at shutdown is sent when Bigarr comes back. Deliveries and their outcome are visible per endpoint, with a retry button. An endpoint can be limited to tags, like a Radarr connection: it then only hears about films whose versions carry one of them (health and test events always go through). It can also speak **Radarr's webhook format** instead of Bigarr's, so tools written for Radarr (Notifiarr, autoscan, autopulse, a Discord bot that reads Radarr webhooks…) work unchanged: the bodies are Radarr's (`Grab`, `Download`, `Rename`, `MovieAdded`, `MovieDelete`, `MovieFileDelete`, `Health`, `HealthRestored`, `ManualInteractionRequired`, `Test`), a Radarr movie is a version picked by the endpoint's view, as for an API key (`movie.id` is the `/api/v3/movie` id), and the events Radarr has no word for (`downloadFailed`, `versionAdded`, `versionUpdated`, `versionDeleted`, `defaultVersionChanged`) are not sent. Bigarr's own `data` carries everything Radarr's bodies do and more. A Discord channel webhook reads neither body, since Discord only takes its own messages: the **Discord format** posts to one (`https://discord.com/api/webhooks/{id}/{token}`) the embeds of Radarr's Discord connection, same colors and fields (overview, rating, genres, quality, group, size, links, release, poster, fanart, indexer, custom formats, tags, picked per kind of message, with the webhook's username, avatar and author), plus what Radarr does not post: the version, the failed downloads and imports, and the versions added, deleted or made the default. Texts are cut to Discord's limits, a 429 is retried after the delay Discord asks for, and the webhook's token never reaches the logs; a Discord URL saved with the Bigarr or Radarr format is refused. `Bigarr__Notifications__ApplicationUrl` fills Radarr's `applicationUrl` and `instance.applicationUrl`, for links back to Bigarr.

System → Status shows the **health checks** (no indexer or download client configured, an indexer paused after failures, an unreachable client, a missing root folder, an RSS loop that stopped running, ffprobe not found, imports that had to copy instead of hardlink, a failing webhook, a metadata refresh that did not finish; `GET /api/v1/health`) and the **scheduled tasks** (RSS sync, search missing and cutoff unmet, health check, media maintenance, metadata refresh, weekly backup) with their last run, its outcome and the next one; each can be run now, from the page or with `POST /api/v1/system/tasks/{name}/run`. The scheduler remembers the last run of each task across restarts, so a restart does not hammer the indexers (`Bigarr__Scheduler__Enabled` switches it off; the tasks then only run on demand).

**Connecting other apps.** Bigarr answers as a Radarr v5 on `/api/v3` (plus `/signalr/messages` and `/MediaCover`), so anything that talks to Radarr talks to Bigarr: create a key in Settings → Connect and give the app Bigarr's URL and that key (`X-Api-Key` header or `?apikey=` both work). What makes it more than a Radarr is the key's **view**: `default` shows each film as its default version, like a classic Radarr; `all` shows one line per version, so Bazarr subtitles every file; `version:<name>` shows only the version of that name and creates it when the app adds a film. A movie id on `/api/v3` is therefore a **version** id, and `titleSlug` (the TMDB id) is what the versions of a film share. The practical recipe: one **Seerr**, two Radarr servers pointing at the same Bigarr, a standard one with a `version:1080p` key and a 4K one with a `version:4k` key; each request creates or follows its own version and neither server notices the other. **Bazarr** keeps one line per TMDB id, so it cannot take the `all` view: run one Bazarr per version, as the usual Bazarr + Bazarr 4K pair, with a `version:1080p` key on the first and a `version:4k` key on the second; each hears about its imports, upgrades, renames and deletions live over SignalR, filtered by its view like every other route. **Prowlarr** adds Bigarr as a Radarr application and pushes its torrent indexers through `/indexer`, `/indexer/schema` and `/indexer/test` (setup above). Commands accepted: `MoviesSearch`, `MissingMoviesSearch`, `RefreshMovie`, `RescanMovie`, `RefreshMonitoredDownloads`, `RssSync`. The human session never opens `/api/v3`, and a key never opens the UI.

**Series: the Sonarr side.** Sonarr and Radarr answer the same routes (`/api/v3/system/status`, `/api/v3/queue`…), so Bigarr speaks Sonarr v4 under its own URL base, `/sonarr` (`/sonarr/api/v3`, `/sonarr/MediaCover`), the way a Sonarr behind a reverse proxy is set up; every client has the field (Seerr's *URL Base*, Bazarr's *Base URL*, the path of Prowlarr's *Sonarr Server*). The same keys and views apply: a series id is a **series version** id, `titleSlug` is the TVDB id, and an episode id is the episode's own, shared by the versions of the show, its `monitored`, `hasFile` and `episodeFile` being those of the version the key reads it through. The recipe is the films' one: one **Seerr** with two Sonarr servers (`version:1080p` and `version:4k` keys) requests seasons, each server creating or following its own version of the show (a request without `addOptions.monitor`, as Seerr sends it, monitors the episodes of the seasons it asks for); one **Bazarr** per version reads series, episodes with their files (`includeEpisodeFile=true`), `/episodefile` and the grabs' `nzbInfoUrl` in `/history`; **Prowlarr** adds Bigarr as a Sonarr application, and an indexer it pushes to both apps stays one indexer here, the Radarr sync writing its film categories and the Sonarr sync its series and anime ones. The queue has one record per (download, episode): a season pack is as many records as it has episodes. A key with the `all` view reads every version but writes nothing (episode ids are shared, it designates no version). Shows without a TVDB id are left out. Commands accepted: `MissingEpisodeSearch`, `SeriesSearch`, `SeasonSearch`, `EpisodeSearch`, `CutoffUnmetEpisodeSearch`, `RescanSeries`, `RefreshSeries`, `RefreshMonitoredDownloads`, `RssSync`; any other is accepted and does nothing.

**Moving in from Radarr.** Settings → Import from Radarr reads an existing Radarr over its API (URL and key) and shows what it holds before writing anything: its quality profiles against Bigarr's (matched by name, or by what the name says about resolution), its root folders against Bigarr's (a Radarr path that exists on this host needs no translation; otherwise pick the Bigarr root folder that holds the same files), its tags, and how many films are already here. Every Radarr movie then becomes **one version** of the film, named after the Radarr it comes from: `1080p` for a standard Radarr, `4k` for a 4K one, so importing a second Radarr with another name adds second versions to the same films instead of duplicating them. The version keeps Radarr's monitored flag, quality profile, minimum availability and tags; the file is attached when it is found under the mapped root folder and probed later by the media maintenance task; films without a file become fileless versions; import exclusions come along. Each mapped Bigarr profile takes the settings of its Radarr profile: the custom formats with their scores and score thresholds, and the qualities (which are allowed, their order and groups, the cutoff, whether upgrades are allowed); when several Radarr profiles map to one Bigarr profile, the one holding the most films wins. Metadata comes from Radarr's own payload, so a library of thousands imports in seconds with no TMDB round trip; the film is flagged for a metadata refresh. A film that already has a version of that name is **updated**, not duplicated, so the import can be re-run, and it also repairs a library that was scanned first (everything a scan finds is unmonitored). The report lists every file Radarr knew that was not found, and every film skipped for an unmapped profile or root folder. In-flight downloads are not migrated: point Bigarr's download client at Radarr's category and stop Radarr before, or both will import.

**Shadow mode: comparing with Radarr before replacing it.** With `Bigarr__Shadow__Enabled=true` Bigarr runs next to the Radarrs it is meant to replace and never sends anything to a download client: the RSS pass, the searches and the interactive grab record what they would have grabbed (*picks*), and the health check says so with a notice instead of warning about the missing client. A pick is treated as the file it would have become: the RSS pass and the searches judge later releases against a version's latest pick, so Bigarr picks again only when a release upgrades it, as it would grab again only an upgrade once that download was imported. Settings → Followed Radarrs holds those Radarrs (URL, API key, the version their films are, and the import's profile and root folder mapping; the import's *Keep following this Radarr afterwards* fills it in). Every 15 minutes Bigarr reads each one, with GET requests only: its profiles, which the mapped Bigarr profiles keep following (qualities, cutoff, scores), so both judge with the same settings; its history since the last pass, whose grabs are kept and judged by Bigarr's own engine against the film as it was before the download (or against Bigarr's own pick, when it had made one before); the films added to it since, which come in through the import's mapping and get Bigarr's own search on add; and the files it imports, upgrades, renames or deletes, which become the version's file record in Bigarr's database (nothing is written to disk). A webhook added in Radarr (Settings → Connect → Webhook, the URL the settings page shows, with a Bigarr API key) makes those passes run within seconds of a Radarr event. Activity → Compare, and the page of each film concerned, pair Radarr's grabs with Bigarr's picks, by release and otherwise by film and version within a window: same release, different release, Bigarr only, Radarr only, each with the reasons on both sides, including Radarr's own parse of Bigarr's picks and whether Bigarr's feeds ever carried what Radarr took.

**The library page.** Two layouts: posters, and a table with a column chooser where a click anywhere on a row opens the film. Sort by title, year, date added, size, quality or rating: click a column header in the table (again to reverse it), or pick it in the View menu for the posters. A film's size adds up its versions' files; under it, *Size per version* (on by default, in the column and card lists) shows how it splits, `1080p 39 GB · 4k 82 GB`, and the chevron next to the Size header sorts by one version's file instead, films without that file last. Filter on monitoring, status, quality, tags, root folder, the versions a film has or lacks, and when it was added. Monitoring, status, quality, tags and root folder match when any version of the film does; *Applies to* narrows them to every version, the default one or a named one. Each version chip is coloured by its state (green for a file that needs no upgrade, violet with an arrow below the cutoff, amber missing, blue downloading, grey not out yet), dashed when unmonitored and starred for the default version; hovering it spells that out. Preset tabs with live counts cover the daily questions (missing, missing `4k` for the second and third most common version names, cutoff unmet, recently added, unmonitored), a dot before the label giving the colour of the chips they list, and *Save view* keeps the current filter, sort and layout under a name. The View menu also sets the poster size, what a card shows, the table columns and the density. These preferences are kept per user, in the browser. `/?view=table&preset=missing-4k` opens the page on a layout and a view.

**Storage.** Settings → Library shows, above the root folders, the space each root folder holds (movie files only: extra files have no stored size) and the free space left. The free space appears only when every root folder reports it, and a drive shared by several root folders counts once. A click on a folder opens the library on the films with a file in it, biggest first (`/?view=table&rootFolder=2`), sorted by the size of the version name that holds most of the folder (`4k` for `/movies-4k`), so the films' files in other folders do not count.

**Editing the library in bulk.** On the library page, *Select* turns cards and rows into checkboxes (shift-click selects a range; select everything, or everything the current filter shows). The toolbar then acts on **one version of each selected film**, chosen in the toolbar: the default version, a version name such as `4k`, or all versions. It monitors or unmonitors, sets the quality profile, the minimum availability or the tags (add, remove or replace), queues an automatic search, or deletes. Films without that version are skipped and listed in the report. Deleting the default version of a film that has others hands the default over to its oldest managed version; deleting a film's only version, or choosing *all versions*, deletes the film, with its files (through the recycle bin) and an import exclusion if asked. The confirmation states what will happen before anything does: versions and films deleted, files and where they go, new defaults, films skipped. Every changed version publishes the same events as a change made on the movie page, so Seerr, Bazarr and the media servers follow. The endpoints are `PUT /api/v1/movies/bulk`, `POST /api/v1/movies/bulk/search` and `POST /api/v1/movies/bulk/delete` (with `dryRun`).

**Media servers.** Settings → Media servers holds the Plex, Jellyfin and Emby servers to keep informed: URL, token (a Plex token, or an API key), and a path mapping when the server mounts the library under another path than Bigarr does. Every imported, upgraded, renamed or deleted file makes each enabled server scan **that folder** (Plex: the section whose location contains it, with the path; Jellyfin and Emby: `Library/Media/Updated`), so the film shows up without waiting for the server's own schedule. A server that does not answer is retried a few times with growing delays; the last outcome is on the row, a failing server is a health warning, and a full scan can be run from the page. This is the connection Phase 3 will reuse for sessions and statistics.

**Backups.** System → Status lists them and makes one on demand (`POST /api/v1/system/backup`): a zip of a consistent snapshot of the database plus a manifest, under `<config>/backups`. A scheduled backup runs every `Bigarr__Backup__IntervalDays` (7) and prunes anything older than `Bigarr__Backup__RetentionDays` (28). Restoring stages the database next to the live one and stops the process; on the next start (the container restarts on its own) the staged file is swapped in, the previous database is kept as `bigarr.db.before-restore`, and pending migrations are applied. To restore on a fresh host, drop the zip into `<config>/backups` and restore it from the page.

On first start an `admin` account is created. Set `Bigarr__InitialAdminPassword` to choose its password; otherwise a random one is generated and printed once in the logs.

## Deployment

A multi-arch image (amd64, arm64) is published to `ghcr.io/hezflix/bigarr` on every merge to `main`. See [`deploy/docker-compose.example.yml`](deploy/docker-compose.example.yml). Downloads and libraries must live under **one shared mount**, otherwise hardlinks are impossible and imports fall back to copies.

Behind a reverse proxy, forward `X-Forwarded-For` and `X-Forwarded-Proto` (Traefik and nginx do by default): Bigarr trusts them from any address, marks the session cookie Secure on https and logs the real client on a failed login. An SSO in front of Bigarr (oauth2-proxy, Authelia…) must leave `/api/v3`, `/signalr`, `/MediaCover` and `/sonarr` alone, or the apps must reach Bigarr over the internal network: those paths are protected by the API key, and Seerr, Bazarr and Prowlarr cannot sign in to an SSO.
